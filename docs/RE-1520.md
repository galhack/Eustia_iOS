## 1. Summary

- `data/BGI.exe` is **packed/encrypted** (Alpha-ROM-class) and cannot yield the
  opcode tables statically: no family message strings, no tables, and the image
  faults when executed without its external unpacker. `optables.py` therefore
  cannot dump it — this is a property of the artefact, not of the tool chain
  (the tool was hardened to say so instead of crashing).
- The opcode set has to be recovered as a **proxy**: the game's own original
  1.520.6 programs (`data/Original_file`) show which opcodes 1.520.6 actually
  defines and uses. They use opcodes that 1.494 lacks (family `81`, `81 60`,
  `90 06`, `81 30`, `81 1e`, `81 63`, `81 64`, `81 0f`, `92 17`, `B0 06`, …)
  and nothing outside the 1.529 survey row. The 1.520 row is therefore taken as
  the **1.529 row**, a superset of the observed need (`tools/re/opset_1520.txt`,
  `tools/re/opdiff_1520.txt`).
- Only **two** opcodes need new handlers: `A0 23` (used by `scrsnd._bp`) and
  `main 77` (used by `dbgmngr._bp`). The other 21 `--list-missing` entries are
  referenced by no program. Specs in `docs/RE-1520-OPCODES.md`.
- The game is **1280x720**: ipl sets display mode 6 and the projection centre
  (640,360); the 1.494+ size table's entry 6 is 1280x720; all 5163 pictures are
  1280x720-family. The `set_size_entry(7,1280,960)` call rewrites the unused
  fullscreen entry 7.
- **Tagged-pointer layout is B, not C**: all tagged-pointer constants in the
  original 1.520.6 programs (137 of them) are `tag 8 << 25` code pointers and
  `tag 0xA << 25` heap pointers; there is no 26-bit layout-C constant anywhere.
  The 1.520 profile should therefore use `tagShift 25, tagCode 8, tagData 9,
  tagHeap 0x0A, dynFirst 0x10, dynCount 48, heapLimit 32 MB` (LAYOUT_B) with
  the 1.529 opcode row and behaviour level. Display, boot areas and anti-tamper
  are below.
- Assets: **all 5163 CompressedBG pictures are version 1** (no v2 anywhere);
  all 38539 BW sound files are **Ogg Vorbis** (44.1 kHz, mono SE / stereo BGM),
  the 8 movies are **MPEG-1 program streams 1280x720 30 fps + MP2 stereo** in
  `data02840.arc` only.
- Chinese patch: scripts are **GBK**, not at Shift-JIS character boundaries
  (90% of the two-byte characters have a lead byte in 0xA1..0xDF, which is the
  SJIS single-byte range), so the Windows patch must patch the engine's text
  handling; V1.1 does it with a Detours `Game.dll` that forces the GDI face
  黑体 and redirects file reads into `GameData.dat`, V1.5 with an injected
  shellcode launcher. For the Apple port only the *conclusions* matter (GBK
  decode + a Heiti-family face), which the engine's Apple back end already
  implements.

## 2. The executable is packed

### 2.1 Layout (observed, `pefile`)

`data/BGI.exe` (4 513 792 bytes, 2011-04-28), PE32, ImageBase 0x400000,
entry RVA 0x55FD3, `SizeOfImage` 0x89B000:

| section | RVA | raw | virtual | entropy | characteristics |
|---|---|---|---|---|---|
| `.text` | 0x1000 | 0x55000 | **0x143000** | 7.98 | RWX |
| `.rsrc` | 0x144000 | 0x4d000 | 0x8ba18 | 7.99 | RWX (icons; directory is intact) |
| `.idata` | 0x1d0000 | 0x1000 | 0x1000 | 1.50 | RWX (real import descriptors) |
| `.data` | 0x1d1000 | 0x1000 | 0x321000 | 0.04 | RWX (BSS, 16 non-zero bytes) |
| `.data` | 0x4f2000 | 0x3a8000 | 0x3a8000 | 7.69–7.93 | RWX (packed payload + icon/version data) |
| `.data` | 0x89a000 | 0x1000 | 0x1000 | 1.25 | RWX (packer stub) |

Facts that make this a packed image and not a normal VC6 build:

- `.text` has a **raw size far below its virtual size** and entropy 7.98 (a
  normal code section is 6.4–6.8 and raw ≈ virtual).
- the code/data sections are RWX (not merely RX) and `.rsrc`/`.idata` are RW,
  the section names are partly garbage
  (`.data\0.t`, `.data\0\xd6\x06`), and the import table is a decoy: 17 DLL
  descriptors with **one API each** (kernel32 `lstrcpy`, user32
  `GetKeyboardType`, gdi32 `UnrealizeObject`, imm32
  `ImmSetCompositionWindow`, …) — not the imports of an engine that draws,
  plays audio and reads archives.
- **no BGI family message string exists in the file**: `未定義の基本命令`,
  the `$80%02X`/`$90%02X`/`$A0%02X` message forms, the user-op message and the
  engine version text are absent as readable CP932/ASCII (the isolated `$80`
  byte run at file offset 0x9ae407 is inside the compressed `.text` data and
  not a string).
  The only readable data is the resource tree (icons, dialogs, version
  resource "Version : 1.520.6 / Compatibility : 1.69", by BURIKO 2007–2011)
  and the import/export directories.
- PE entry 0x55FD3 disassembles to junk (`push edx; mov edx,0x64; …` loop with
  uninitialised registers, a `lstrcpy(esp,esp)` call, then `jmp 0xc9a000`).
  The tail section then contains an obfuscated stub: a hash/key-derivation
  routine at 0x89A038, a **dword decryptor** `for each dword: v = (v ^ key1) +
  key2` at 0x89A14C (called at 0x89A106 with dest = section VA 0x8F2000/0x4F2000,
  length 0x1000, key1 0x30EEE628, key2 0x0163EAD5), and a self-modifying jump
  at 0x89A000. The first 0x1000 bytes of the big `.data` are what that stub
  decrypts — i.e. the real unpacker is built at run time from encrypted data.
- the same packing appears in **both** copies in the install:
  `BGI.exe` (2011-04-28) and `BGI.exe.OLD` (2011-02-28) have identical section
  tables and hashes except for **3 bytes at file offset 0x364675** inside the
  big `.data` (a tiny flag patch), and the V1.1 patch's `BGI_CHS.exe` is the
  same image plus a `.detour` section (RVA 0x89B000, virtual 0x628 bytes — the
  Detours bootstrap that loads the patch DLL).

### 2.2 What was tried, and the result

- `tools/re/optables.py data/BGI.exe`: hardened copy reports that none of the
  family messages exist and therefore no tables can be located (the original
  copy raised `struct.error` inside `pe.code_refs` after `string_va` returned
  `None`; `tools/re/pe.py` was also made section-agnostic — it used to demand a
  `.text` section that this image's odd layout still has, but the packed image
  has no usable code section either).
- Reading the stub by hand: the entry code is deliberately broken for a static
  reader and the stage-1 decryptor only decrypts 0x1000 bytes of `.data`;
  there is no reachable second stage in the stored bytes. See §2.1.
- **Dynamic attempt** (cheap, no game data modified): CrossOver 26.3/Wine 11 is
  installed; a throwaway prefix under `build/wineprefix` runs Win32 PE code.
  `BGI.exe` launched directly faults at `EIP 0xfff50de4` ("page fault on read
  access … in wow64 32-bit code") — exactly the obfuscated entry path — and
  stays crashed (1 thread). The V1.5 launcher
  `秽翼的尤斯蒂娅.exe` starts `BGI.exe` but does not prevent the fault (it
  needs `cnprj.dat`, which the install does not contain); the V1.1
  `BGI_CHS.exe` (+`Game.dll`+`detoured.dll`+`Game_CHS/GameData.dat`) faults at
  the same address. No unpacked image can be dumped because the process dies
  before the unpacker runs. (This also corroborates the static reading: the
  stored image is not runnable without its external crack/unpacker.)
- Conclusion: the exact 1.520.6 opcode table is **not statically recoverable
  from this artefact**, and the task's deliverables 1/4 are produced by the
  proxy method below, with that limitation stated. The lead's instruction "do
  not burn the budget on Alpha-ROM unpacking" is followed.

Tool changes made: `tools/re/pe.py` rewritten (section-agnostic, `str` searches
CP932/ASCII and tolerates absent strings, adds `sections`/`info` commands) and
`optables.py` hardened (`string_va` returns a list, families that cannot be
found are reported, candidate tables validated) so the packed exe produces a
diagnosis instead of a crash. `tools/re/mk_opset_1520.py` generates the proxy
deliverables.

## 3. Opcode set recovery

### 3.1 The data that settles the lower bound

The install contains the **original Japanese data** in `data/Original_file`
(`data01000.arc`, `data02800.arc`, `sysgrp.arc`, `sysprg.arc`, `system.arc`;
2011-02-28, i.e. Buriko's own 1.520.6-era programs, not the translation). That
lets us recover the opcode set the engine must define, independent of the patch.

Method (`tools/re/mk_opset_1520.py`): `bpasm -l` both archives, `bpasm -d -b`
every `._bp` (1 + 67 programs), map every mnemonic back to an opcode through
`src/asm/opnames.c`, and compare with the generation rows of
`src/vm/opset.c`. Result:

- **All 234 773 instructions** of the 68 programs were decoded from their own
  bytes (not from mnemonics, which are renumbered across generations) and every
  one uses an opcode defined in the 1.529 row: no instruction outside that row
  occurs, so 1.529 is a valid upper bound for the profile.
- The programs **do** use opcodes that the 1.494 row does not define; that
  settles "1.520 is not just 1.494": `main 66`; `81 0F 1E 30 63 64`; `90 06`;
  `91 1D 55`; `92 17`; `A0 23`; `B0 06` (asterisks in
  `tools/re/opdiff_1520.txt`). The original ipl itself uses `81 60`
  (set_size_entry), `80 60` (set_display_mode) and `90 06` (set_proj_centre);
  the other additions appear in the other programs (`81 30` load_file_range_raw,
  `81 1e` simulate_click, `81 63` set_fullscreen_fit, `81 64` set_window_size,
  `81 0f` is_iconic).
- The two unnamed opcodes (defined in the profile, no OpenBGI handler) are
  **`A0 23`** (`scrsnd._bp`) and **`main 77`** (`dbgmngr._bp`) — in both the
  original and the patched programs. Everything else in the 23-entry
  `--list-missing` list is dead for this game. (`main 7C`, `80 27 EA`, `81 F2`,
  `90 92`, `91 69 70 71 73 74 75 76 78 79 7A 7B 7C 7D BB`, `92 13`, `B0 22`.)
- Scenario `.bcs` files are a **different bytecode** interpreted by
  `scrdrv._bp`/`scrctrl._bp` + the `scr*` programs (docs/scenario.md), so the
  VM opcode scope is exactly the 69 `._bp` programs. This was verified against
  `engine/openbgi/docs/scenario.md`.

### 3.2 The 1.520 row used

`tools/re/opset_1520.txt` is the **1.529 row** of `src/vm/opset.c` written in
`optables.py` dump format (so `insert_gen.py` can insert it as a new bit); the
table addresses are unknown (packed exe) and are written as `00000000`.
`tools/re/opdiff_1520.txt` compares it with 1.494 (additions, with `*` marking
the ones the original programs reference) and with 1.647 (context: the 1.647
build defines many more opcodes later).

Note for the engine: because the profile's generation decides both the opcode
row *and* the registered handler ranges, the 1.520 profile must sit **after
GEN_1_529** in `EngineGen_t` for the 1.529-on handlers (`90 06`, `81 60`, …) to
be live. The current engine tree already orders it that way
(`src/core/version.c`: 1.494, 1.529, 1.520, 1.535, …) which matches this
evidence.

## 4. VM parameters

### 4.1 Display, resolution

Observed in the original ipl (disassembly of `Original_file/system.arc` ipl._bp,
same code in the patched one):

```
sys81.set_size_entry(7, 1280, 960)
sys.set_display_mode(6, 1, 0)
gfx0.set_proj_centre(1280/2, 720/2)          # 640, 360
```

- `set_display_mode(6, …)` selects size-table entry 6 of the 1.494+ table in
  `src/sys/display.c` (`w494/h494`): **entry 6 = 1280x720**. The engine's
  `Display_SetSizeEntry` then overwrites entry 7 (the fullscreen 1920x1080 slot)
  with 1280x960 — entry 6 is untouched.
- The projection centre 640,360 is exactly half of 1280x720.
- Asset survey confirms: the picture size histogram is `1280x720` (1267),
  `500x720` (1202), `690x360` (1192), `1320x720` (867), small UI pieces.
  No 4:3 or 960-tall screen-sized picture exists.
- `gfx0.font_cache(1, 28, 100, 0, 1024)` and every `gfx1.window_set_font(h, 1,
  28, 100, …)` use size 28 px, width 100%, i.e. the default text metrics are in
  720p pixels.

### 4.2 Tagged pointers: layout B (25-bit offsets)

All `push_i32` immediates of the 68 original programs were extracted from the
`bpasm -d -b` listings (6983 immediates, 251 distinct values) and classified:

| value pattern | count | tag at shift 25 | meaning |
|---|---|---|---|
| 0x10000000–0x10000100 | **137** | **8** | code-area pointers (`tagCode`), offsets 0..0x100 |
| 0x14xxxxxx | 5 | **0xA** | local-heap pointers (`tagHeap`) |
| everything else | — | 0 / plain ints | data values, masks (-1, 0x80000000, …) |

There is **no** constant with a 26-bit layout-C code tag (`tag 1 << 26 =
0x04000000` would be tag 2 at shift 25 and does not occur). The same counts
appear in the Chinese patch's programs, so this is the *compiler ABI of the
shipped engine*, not a patch quirk. Layout B = `tagShift 25, tagCode 8,
tagData 9, tagHeap 0x0A, dynFirst 0x10, dynCount 48, heapLimit 32 MB`
(cf. `inc/bgi/version.h` LAYOUT_B; the engine currently ships the 1.520 profile
with LAYOUT_C and should be changed to LAYOUT_B).

Example (original `gstcnfgwnd._bp`): `push_i32 code(dat_0001)` is stored as
`02 01 00 00 10` = 0x10000001, `…dat_0006` = 0x10000006 — tag 8, 25-bit offset.
`bsctrl._bp` uses 0x10000000 likewise.

Runtime check performed: LAYOUT_B and LAYOUT_C profiles (both with the 1.529
opcode row and BOOT_B) boot the Chinese data to the title; at 32 s the two
screenshots are byte-identical (1280x720) and no script errors appear, so the
title path does not exercise the difference. Screens that hand tagged pointers
to handlers (config window punch tables, `bsctrl` `obj_get_param` with
`0x10000000`) are the discriminating ones; with LAYOUT_C those constants decode
to invalid tag 4. Recommendation: LAYOUT_B, and keep the config/backlog screen
as the acceptance test.

### 4.3 Boot areas, heap, dynamic blocks

- Boot thread areas are not observable from the data files (they are engine
  constants of the original EXE, which is packed). BOOT_B (code 512 KB, data
  256 KB) is the build range the 1.520-era siblings use (1.69/472 … 1.529) and
  both BOOT_A and BOOT_B boot to the title; keep BOOT_B.
- `ipl._bp` calls `sys.set_gmem_size(8)` (8 MB global memory) and computes the
  bitmap cache size from `sys.get_memstatus()`; it checks the "common area"
  address constant `0x43088` against 1 MB (a sanity check on the global area).
- Child threads spawned by ipl: `sysmsg._bp` with (512, 32768, 32768) and
  `emergency._bp` with (256, 16384, 16384) — small per-thread code/data areas,
  consistent with the 1.69+ hardware.
- LAYOUT_B's dynamic-block pool (`dynFirst 0x10`, `dynCount 48`, 32 MB heap)
  follows from §4.2.

## 5. Generation behaviour switches — which side is 1.520 on?

`EngineGen_t` thresholds appear in ~130 lines of the engine source (plus
registration ranges). The decision for the new generation:

**Rule used:** 1.520.6 (built 2011-04-28) is *between 1.494 (2010) and 1.529
(2011-07)* by version number, but its own programs use 1.529-row opcodes. So:

- **≤ 1.494 thresholds: ON** (the engine is newer than 1.494 by any reading;
  e.g. `src/sys/display.c`'s 8-entry size table — needed for entry 6 = 1280x720;
  `src/core/loadfile.c` 64 MB file limit; the 1.494 markup tags; the
  `80 60` size-index check).
- **= 1.529 thresholds: ON** (documented as "1.520.6 already has the 1.529
  feature level" in the code at `src/core/version.c`). Evidence per switch:
  - `src/sys/input.c:145` keys-when-inactive (81 14) / `:360,365` standard-key
    groups 0x40000000, 0x80000000 — the original programs call
    `sys.set_standard_key` (97 call sites) and `81 1e simulate_click`, so the
    1.529 key API is present.
  - `src/gfx/window/window.c:156-157` window size limits 0x780 x 0x8000 (1.529)
    vs 0x400 x 0x300 — the game's windows are up to 1280 wide, so the 1.529
    limit is required (`sys81.set_window_size` / window_create in scrsys etc.).
  - `src/gfx/text/strings.c:75`, `src/gfx/text/layout_common.c:139` font extra
    width (`91 0F`): the game uses proportional windows (`scrslct._bp`,
    `scrmsg._bp` pass `prop = 1` in window_set_font), so the 1.529 metric path
    applies.
  - `src/gfx/text/markup.c:28-34,406` markup tags `r //r c /c l /l`; the game's
    text uses ruby/markup (original scenarios include ruby tags; `msgwndctrl`
    calls `set_ruby_font`, `ruby_parse`).
- **≥ 1.535 thresholds: OFF** (1.535/Gackoh is 2012, after this game). Those
  lines are mostly opcode registration ranges (1.535+ opcodes simply are not in
  the 1.529 opcode row, so they cannot be used), plus a few behaviour checks
  (`src/vm/ops_gfx0.c:443` gray-slot validation, `src/gfx/dispobj.c:757`
  priority/fixed position, `src/gfx/text/markup.c:30` `cr` tag, …). None of
  them can be active in a 1.520 build; the 1.529 row already prevents their
  opcodes from decoding, and the 1.520 profile must not enable them.

Every generation *comparison* in `engine/openbgi/src` (78 lines, 37 ON and 41
OFF for a 1.529-level 1.520 profile) is listed with its decided side in
**`tools/re/gen_switches_1520.txt`**, generated with the rule above; the file
also states the registration-range policy. The only ambiguous threshold for
1.520 is 1.529, and the data settles it: ON. (`grep -rn "GEN_1_"` additionally
returns the opcode registration tables and profile rows — 413 lines — which are
not behaviour switches.)

## 6. Anti-tamper / product checks

`ipl._bp` (original and patched, offset 0x164..0x180 inclusive):

```
sys.get_product_name(buf)
if (streq(buf, "AiyokunoEustia_Product") == 0) quit
if (!debugInf && sys.file_exists(0, "AiyokunoEustia")) quit
```

- The engine's product name must be exactly `AiyokunoEustia_Product` (that is
  what `games.json`'s `"product"` sets; the engine build carries it as its
  product literal, which also names the save data and the uninstaller mutex).
- `AiyokunoEustia` is the **disc marker** file the discs carry; its presence
  next to the game makes the boot program quit. OpenBGI hides it by default
  (`--disc-marker` makes it visible), which is the right behaviour for the
  port — the marker must not exist in an app bundle anyway.
- `debug.inf` (checked earlier at 0x15e) enables the debug manager
  (`dbgmngr._bp`); it must **not** exist for players. This is also the only
  program that uses `main 77`.
- No integrity hash check runs in normal play: `BGI.hvl` (72 bytes/record:
  file name + 16-byte hash; lists `BHVC.exe`, `system.arc`, `sysprg.arc`, …) is
  used only by the installer/repair path (`Hvl_Load` in
  `src/sys/install/hvl.c`, `81 E9` hash ops are not called by any program).
  The patched arcs do not match the original `BGI.hvl`, which is exactly why
  the Chinese patch has to bypass/ignore it on Windows.

### 7.1 CompressedBG

- **All 5163 are version 1** (the version word at +0x2E is never 2). The engine
  therefore needs only the v1 decoder for this game; the v2 decoder
  (`cbg2.c`) is not exercised. Header checked on every entry:
  `CompressedBG___\0`, u16 w +0x10, u16 h +0x12, u32 bpp +0x14, u32 key +0x24,
  u32 encLen +0x28, u8 sum/xor +0x2c/+0x2d, u16 version +0x2e.
- bpp: 32 (4396), 24 (658), 8 (109). Size histogram: 1280x720 (1267),
  500x720 (1202), 690x360 (1192), 1320x720 (867), 202x112 (218), 990x720
  (120), 218x528 (46), 450x200 (24), 1280x50 (16), 460x110, 1280x80, 1280x60 …
  (the narrow/tall ones are UI parts and character face parts).
- Checked a sample by decoding: `face_010027` = 1280x720 32 bpp v1
  (`data02001.arc`), `SGBackLog000100` = DSC + 240x120 32 bpp raw.

### 7.2 Sound (BW)

Every one of the 38 539 entries is a BW file with a 4-byte length prefix
(0x40) then the 0x40-byte `bw  ` header; **codec 3 = Ogg Vorbis in all of
them** (no PCM/ADPCM/Huffman). Rate/channels: 44 100 Hz/1 ch (37 922, sound
effects), 44 100 Hz/2 ch (604, music), 22 050 Hz/2 ch (11), 22 050 Hz/1 ch
(2). Music is stored as head/loop pairs (204 `*_head`/`*_loop` entries, e.g.
`data05000.arc` 60 tracks × 2; `81 30 load_file_range_raw` reads the pair).
`system.arc` also carries five `sse99xxxx` SE banks (DSC-compressed, ~54 KB
decoded each).

`--movie=ARC:NAME` test path and the sp-mpeg-style decoder must accept an
archive-range source. No `BF_Movie` sequence exists in this game (the format of
1.69/472+ is absent), and no movie is stored as `data*.dat`.

`data02002.dat` (7 700 480 bytes, next to `data02002.arc`): high entropy, a
0x800-byte periodic structure, no known BGI magic, and referenced by **no**
program (the only `.dat` name used by the programs is `ISEforEustia.dat`, the
initial-settings file of `ISEforEustia.exe`). It is not needed by any asset
path exercised by the engine; treat it as leftover/DRM data and ignore it.

### 7.4 Scenario and fonts

- `data01000.arc`: 205 `BurikoCompiledScriptVer1.00` files (one big
  `aiy00010` library + chapters `aiy00020`…). Text is GBK (see §8).
- Fonts requested by the programs: the engine's built-in font numbers only —
  `gfx1.window_set_font(h, 1, 28, 100, bold, prop, rubyReserve)` and
  `gfx0.font_cache(1, 28, 100, 0, 1024)`; number 1 is the engine's built-in
  **ＭＳ 明朝 (MS Mincho)** (`MSG_FONT_MINCHO`), number 0 is **ＭＳ ゴシック**
  (`MSG_FONT_GOTHIC`). No program registers a font by name (`ext0.font_register`
  B0 C0/C1 and the font-file opcodes B0 C2/C3 are unused), so the Windows face
  comes from the engine's two hard-coded names — which is why the Chinese patch
  had to force 黑体 globally.
- No **user-defined `FF xx` opcodes** are used anywhere: none of the 69 programs
  contain an `FF` instruction; the user-op mechanism (`FF F0` register, `FF
  slot` call) is never invoked. (The `main FF` dispatcher is defined in the
  profile but is dead for this game.)

## 8. The Chinese patch

### 8.1 Text is GBK and is NOT kept on Shift-JIS boundaries

The scenario strings are GBK bytes. Measured on `aiy00010` (the chapter
library): 11 670 two-byte characters, of which **10 549 (90.4 %) have a lead
byte in 0xA1..0xDF** — the range that Shift-JIS treats as *single-byte*
half-width katakana. If the engine parsed the text as SJIS, most Chinese
characters would be split. Consequences:

- The Windows patch must patch the engine's text pipeline to treat the text as
  GBK (V1.5 injects code through its launcher; V1.1 ships a Detours DLL, see
  below). There is no "rare GBK character with an SJIS-compatible lead byte"
  trick as in the Subarashiki patch — Eustia's text needs real GBK parsing.
- For the Apple port this is already covered: `gAppleChinese` makes
  `TwoByteChar` decode GBK (CoreFoundation `GB_18030_2000`) and the engine's
  Apple font backend classifies full-width/half-width from that; hosttest
  auto-detects the encoding from `data01000.arc` (GBK here, Shift-JIS for the
  original tree) and renders with the CJK cascade.
- Text is a single-byte/NUL-terminated SJIS-style C string inside the scenario
  container; `--chinese` (or the auto detection) is therefore enough; no
  re-encoding of the archives is needed.

### 8.2 The two Windows patches

In the CrossOver bottle
(`…/Gal/秽翼的尤斯蒂亚/汉化补丁/`):

- **V1.1 “魔法少年えすか☆エムカ”** replaces the executable with
  `BGI_CHS.exe` (the packed 1.520.6 image + a `.detour` section) and ships
  `detoured.dll`, `Game.dll` and `Game_CHS/GameData.dat` (296 530 796 bytes).
  `Game.dll` (PE32, ImageBase 0x10000000, built 2011-11) is a Detours-based
  hook library:
  - strings: GBK `黑体` at VA 0x10043380, `BGI_CHS.EXE` at 0x10043388,
    `\Game_CHS\GameData.dat` at 0x10043394; CryptoPP exception strings (the
    data file is encrypted/compressed with Crypto++ — inferred from the
    CryptoPP exception class names in the DLL, not from decoding GameData.dat).
  - it captures the original import pointers (`CreateFontA` IAT 0x10026000,
    `SetWindowTextA/W` 0x10026180/0x10026184, file APIs 0x10026020..) into
    globals and re-hooks them with Detours (`DetourAttach` at 0x10016136 /
    0x10016670, pairs (hook, &original) at 0x100011e0..0x10001230 and
    0x10001950..0x10001990).
  - the **CreateFontA replacement is 0x100019a0**: it pushes the pointer
    0x10043380 (`黑体`) as the `lfFaceName` argument before calling the saved
    original — i.e. **every GDI font in the game is forced to SimHei/黑体**.
    (The `SetWindowTextA/W` replacements translate the window title; the file
    API hooks serve reads from `GameData.dat`, the encrypted translated data.)
- **V1.5 “枫笛汉化组”** does not use a DLL: it ships a launcher
  `秽翼的尤斯蒂娅.exe` (45 568 bytes, Delphi, 2011-05-26) plus updated
  `data01000.arc`, `data02800.arc`, `sysgrp.arc`, `sysprg.arc`, `system.arc`.
  The launcher is a shellcode injector: it resolves `kernel32!GetCurrentProcess`,
  `WriteProcessMemory`, `GetSystemDefaultLangID`, then `CreateProcessA` +
  `VirtualAllocEx` + `WriteProcessMemory` + `CreateRemoteThread` +
  `WaitForSingleObject` and injects a 0x800-byte payload (built by the Delphi
  function at 0x407f3c from embedded code/data at 0x4080d0/0x408138/0x409294;
  the payload imports `GetCurrentProcess`, `WriteProcessMemory`,
  `LoadLibraryA`, `ReadProcessMemory`, `GetProcAddress`, `SetWindowTextW` and
  is used to hook the engine for GBK text + Chinese window titles). It expects
  `bgi.exe` and `cnprj.dat`; **`cnprj.dat` is missing from the installed copy**,
  which is why the launcher alone does not start the game here (and why the
  direct BGI.exe run faults — see §2.2).
- The installed `BGI.exe` is the original packed image with a 3-byte patch vs
  `BGI.exe.OLD` (file offset 0x364675–0x364677), i.e. the Chinese patch flips a
  flag in the packed data section rather than rebuilding the engine.

### 8.3 What the Apple backend must do (recommendation)

1. **Decode script text as GBK** whenever the game data is the Chinese patch
   (already implemented: auto-detect samples `data01000.arc`, `--chinese`
   forces it). Do not expect SJIS character boundaries; `TwoByteChar` must be
   GBK (`GbkChar`).
2. **Use a Heiti/sans face for the Chinese text** and keep a Mincho-like face
   for the original Japanese data. The Windows patch forces 黑体 for *all*
   fonts, so the Apple equivalent is PingFang SC / Heiti SC / Hiragino Sans GB
   with a Core Text cascade for missing glyphs — exactly what
   `src/os/apple/font.c` implements for `gAppleChinese`. No patch font file is
   needed for Eustia (there is no `font.ttf` in the V1.5 install; V1.1 relies
   on the system SimHei).
3. **Text metrics/wrapping:** the patch does not change the engine's layout
   rules — it just turns the strings into GBK and the face into SimHei; full
   width/ink-width wrapping is still the engine's (`TextIsWide` uses the GBK
   lead byte ranges). Keep the engine's 1.529-level text features on (see §5),
   they are what the 28 px, 100 % width, proportional windows in the scripts
   expect.
4. **Window titles**: the Windows hook rewrites titles to Chinese. On Apple the
   game's own `sys.set_title` strings are already GBK in the patched scripts and
   render fine with the GBK decoding; no hook is needed.
5. Ignore `cnprj.dat`/`Game.dll`/`GameData.dat` entirely: the V1.5-style plain
   `.arc` files (what `data/` contains) are the usable data set; the V1.1
   `GameData.dat` is an encrypted virtual file system for the Windows hook and
   is not needed (and not usable) by OpenBGI.
